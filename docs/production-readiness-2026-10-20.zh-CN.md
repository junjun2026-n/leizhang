# 堡垒机生产就绪验证报告

验证日期：2026-10-20。对象：当前 `JUMP_SSH` 代码、Windows 本机运行实例和项目 PostgreSQL。结论：**暂不通过生产上线验收。可用于受控测试、预发布验证，不建议按当前配置直接接入正式生产资源或公网。**

本报告区分代码测试通过、已复现缺陷和尚未完成的生产环境验收。没有将本机验证视为正式渗透测试、容量认证或生产发布批准。本次未切换业务数据库、启用 MFA、修改 TLS 配置或重启运行中的服务。

## 上线阻断项与缺陷

### P1-01：当前运行配置未满足生产传输安全

实测 `PUBLIC_ORIGIN=http://127.0.0.1:8200`、`COOKIE_SECURE=false`、服务绑定 `0.0.0.0:8200`。当前未验证 HTTPS、生产证书和 WSS。密码、会话 Cookie 和终端数据在直接 HTTP 访问链路上没有 TLS 保护。

修复与复验：部署生产域名和 TLS 代理，配置准确的 HTTPS Origin、`COOKIE_SECURE=true`；阻止非受控网络直接访问应用端口；实际验证 HTTPS 登录、安全 Cookie、WSS 连接、证书续期及错误来源拒绝。绑定所有网卡本身不是缺陷，需要由部署网络和反向代理控制入口。

### P1-02：数据库权限存在越权授予及测试迁移越界问题

实际检查发现 `jump_runtime` 对 `public.audit_logs`、`public.recordings`、`public.alembic_version` 仍具有 UPDATE、DELETE 权限。审计和录像目前由触发器阻止变更，**本次未发现已能绕过触发器修改审计记录**；但预期的只追加授权和迁移表隔离未成立。

根因代码：`migrations/versions/0001_initial.py:21`～25 对 `public` 中所有表授予 DML，后续 REVOKE 使用未限定 schema 的表名；`tests/conftest.py:25` 又把 search_path 指向随机测试 schema。在同一数据库运行测试迁移时，会给真实 public 表授予权限，而撤销发生在测试 schema。故不能宣称当前测试完全不影响同数据库 public 权限。后续独立临时数据库中的诊断避免了这一影响。

修复与复验：迁移授予和撤销必须使用同一个经过校验的 schema；测试改用独立数据库，并增加跨 schema 权限不变的回归检查；由独立迁移账号撤销运行账号的审计/录像 UPDATE、DELETE、TRUNCATE 和迁移表权限，然后重新检查有效权限与触发器。本次未执行额外授权整改；测试迁移的副作用已如实记录，当前有效权限仍待整改。

### P1-03：生产只读部署与后台数据库配置保存不兼容

`compose.yaml` 将 app 设置为 `read_only: true`，通过环境变量注入 DATABASE_URL；`.dockerignore` 排除 `.env`。但 `jump_ssh/platform_config.py` 保存数据库配置会写入 `/app/.env`，且在写文件前已提交“数据库配置更新”审计。

在恢复出的隔离数据库中模拟只读配置文件，实际接口返回 **500**。即使允许写文件，环境变量优先于 `.env`，容器重启也可能继续使用原连接；容器重建还会丢失容器内改动。生产管理员不能依赖当前界面完成数据库配置切换。

修复与复验：采用可持久化、受权限保护且有明确优先级的配置机制；或在部署模式中明确禁用数据库写配置操作，返回可理解的原因并走受控运维流程。必须实际验证保存、重启、重建、失败回滚和审计准确性。

### P1-04：正式部署链路及依赖风险尚未验收

本机未发现 Docker/Nginx 可执行程序，未构建生产镜像、未运行 Compose/Nginx 配置验证。当前实际 Python 为 3.10.8，Dockerfile 使用 Python 3.12；不能把当前测试结果直接作为目标镜像测试结果。生产镜像的操作系统包、浏览器端 xterm.js 及 Python 依赖都需要相应漏洞扫描和升级复测。

Python 锁文件扫描已完成，46 个依赖中有 2 个包命中已知漏洞。工具返回 8 条记录，按漏洞 ID 去重后为 **5 项**，具体如下；尤其 AsyncSSH 的事件循环阻塞风险与堡垒机 SSH 客户端链路直接相关，需升级并复验。

### P2-01：健康检查可能对不可工作的实例报正常

`jump_ssh/main.py:96` 的 readiness 只查询 users。在隔离数据库中临时改名 system_accounts 表后，`/health/ready` 仍实际返回 **200**。多账号核心功能所需的表缺失时，负载均衡或监控仍可能判断实例正常。

修复与复验：启动时检查迁移版本和关键表，readiness 包含必要依赖及超时；验证缺表、版本落后、连接池耗尽和数据库断连时准确报未就绪。

### P2-02：应用层请求体限制可被分块传输绕过

`jump_ssh/main.py:66`～69 仅检查 Content-Length。在隔离应用中发送 70002 字节请求：显式 Content-Length 返回 **413**；Transfer-Encoding: chunked、没有 Content-Length 时进入 JSON/Pydantic 处理并返回 **422**，表明应用未在 64KB 处拒绝请求体。

修复与复验：按实际接收字节限制请求体，并保留入口代理限制；测试分块和大体积、慢速请求。已配置的 Nginx `client_max_body_size 64k` 可提供入口保护，但当前实例直接暴露应用端口，且该 Nginx 配置未实测。

### P2-03：恢复、容量和运行保障证据不完整

- 本次恢复数据规模为用户 1、资源 1、系统账号 1、审计 34、录像 0；恢复后凭据解密通过，但没有可供恢复验证的实际录像。测试环境的加密录像用例通过不等于生产录像灾备通过。
- 本地备份和恢复成功，不代表已有自动调度、异地备份、独立密钥备份、保留周期、告警及符合业务 RPO/RTO 的灾备能力。
- 未完成生产 SSH 目标接入、长连接、并发容量、数据库故障、磁盘满、服务异常退出及恢复等演练。
- 当前仅支持单实例、单 worker；重启中断 SSH 会话。若业务要求高可用或不中断升级，现架构不满足。

## 安全策略和业务适配待确认

- 当前唯一启用管理员未开启 MFA。产品按既定需求保留管理员手动启用策略；正式接入敏感资源前，应按组织策略启用或正式接受风险，不能把 MFA 默认关闭本身误报为功能失效。
- 当前 1 个资源未启用 SSH 主机公钥校验。密码登录功能可以保留，但密码认证与服务器身份校验是两件事；敏感资源建议单独启用主机身份核验。
- 当前数据库仍为 `127.0.0.1:55432`，没有切换到此前提出的远程数据库。正式数据库拓扑、最小权限、网络及备份责任需要确认；本次未尝试更改远程数据库。
- 初始管理员交付文件仍存在，ACL 限制为部署用户及 SYSTEM；不属于本次发现的公开泄露，交付后仍需按凭据管理制度处理。
- `--no-proxy-headers` 配合反向代理时，应用记录的客户端 IP 会是代理；当前文档说明可关联 Nginx 日志，但生产追踪关联和代理限流策略尚未实测。
- RDP、SFTP/SCP 文件审计、命令级阻断、外部不可变审计存储、用户目录对接和高可用尚未实现；如业务或合规要求这些能力，不能以现版本替代相应完整堡垒机。

## 上线复验门槛

1. 关闭以上 P1 项，复验 P2 缺陷；如果存在暂不修复项，明确业务负责人接受的风险和限制。
2. 在拟上线 Python、操作系统、镜像和 PostgreSQL 环境执行完整回归及漏洞扫描，不允许关键测试跳过。
3. 在真实 HTTPS/WSS 链路验证用户登录、账号级授权、审批、撤权、录像、管理员 MFA 和客户端审计追踪。
4. 按预期用户数、并发 SSH 数、持续时长和录像量执行容量与故障演练，形成明确阈值。
5. 从独立备份恢复包含授权和录像的完整数据，验证凭据/录像解密和受控 SSH 接入，记录 RPO/RTO。
6. 落实进程托管、网络访问范围、监控告警、证书续期、备份调度及维护回滚，再签署上线验收。
